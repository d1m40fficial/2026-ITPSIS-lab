# Доступ к лабораторным работам по коду

## Что сделано

Работы открываются кодом преподавателя. Карточка закрытой работы помечена «По коду», кнопка «Открыть работу» и прямая ссылка приводят к одному и тому же запросу кода. Проверка идёт в браузере, сервера нет.

Отличие от лекций: код нужен только чтобы открыть работу. ФИО не подписывается, отчёт для преподавателя не формируется, мастер-код не используется.

## Где лежат коды

Коды преподавателя хранятся в `config/access-codes.json`. Файл не публикуется и добавлен в `.gitignore`. Форма — `config/access-codes.example.json`.

```json
{
  "labs": {
    "1": ["КОД-РАБОТЫ-01"],
    "2": ["КОД-РАБОТЫ-02"]
  }
}
```

Ключ — сквозной номер работы от 1 до 12. Значение — массив кодов: один код на группу или несколько, если доступ выдаётся по одному на человека.

## Сборка

```
pnpm run compile:access
```

Скрипт читает `config/access-codes.json` и пишет `public/access-codes.json`: только SHA-256 хеши кодов, без ключа подписи и без мастер-кода. `pnpm run build` вызывает `compile:access` сам.

Если `config/access-codes.json` отсутствует, скрипт ничего не перезаписывает и работы без опубликованных хешей открываются без кода. Так ведётся разработка. Уже собранный и закоммиченный `public/access-codes.json` при этом сохраняется — именно его публикует GitHub Pages.

Код короче 8 символов после нормализации сборка отклоняет: короткие коды перебираются по хешам.

Работа, для которой в файле кодов нет записи, открывается свободно. Так оставляют отдельные работы открытыми и так же ведётся разработка.

## Как проверяется код

Код нормализуется: регистр, пробелы и знаки препинания отбрасываются, остаются символы `0-9` и `A-Z`. Хеш считается через WebCrypto `SHA-256` и сверяется со списком хешей работы. Кириллица и латиница — разные символы, поэтому раскладка важна.

## Срок жизни доступа

Введённый код запоминается в `localStorage` под ключом `itpsis-lab-access:<базовый адрес>` на семь дней. Затем работа снова запрашивает код. Удалить запись можно очисткой данных сайта в браузере.

## Граница защиты, честно

Хеши лежат в файлах сайта, поэтому вооружённый студент может подобрать код перебором по хешам или обойти проверку в инструментах разработчика. На статическом хостинге без сервера это не решается. Что даёт механизм: случайный зритель не открывает работу без кода преподавателя.

Смена любого кода требует пересборки и коммита нового `public/access-codes.json`.

## Проверка в тестах

`tests/site.e2e.ts` проверяет обе стороны. Тест «опубликованные коды закрывают работы» читает реальный `public/access-codes.json`, требует 12 закрытых работ, проверяет плашку «По коду» на всех карточках и отказ на неверный код. Тест «верный код открывает работу» подставляет свой файл кодов, вводит `lr01-testcode9` с пробелами и в другой раскладке регистра и убеждается, что работа открылась и доступ пережил переход по хешу. Остальные тесты имитируют студента, который ввёл код на этой неделе, через `localStorage`.
